# Cron 与 Heartbeat：何时使用

心跳和 cron 任务都可以让您按计划运行任务。本指南帮助您为您的用例选择正确的机制。

## 快速决策指南

| 用例 | 推荐 | 为什么 |
|------|------|------|
| 每 30 分钟检查一次收件箱 | Heartbeat | 与其他检查批量处理，上下文感知 |
| 在上午 9 点准时发送每日报告 | Cron (isolated) | 需要精确时间 |
| 监控日历以获取即将到来的事件 | Heartbeat | 自然适合定期感知 |
| 运行每周深度分析 | Cron (isolated) | 独立任务，可以使用不同的模型 |
| 20 分钟后提醒我 | Cron (main, `--at`) | 一次性精确时间 |
| 后台项目健康检查 | Heartbeat | 搭载在现有周期上 |

## Heartbeat：定期感知

心跳以固定间隔（默认：30 分钟）在**主会话**中运行。它们旨在让代理检查事物并突出显示任何重要内容。

### 何时使用心跳

- **多个定期检查**：与其使用 5 个单独的 cron 任务检查收件箱、日历、天气、通知和项目状态，不如使用单个心跳批量处理所有这些。
- **上下文感知决策**：代理拥有完整的主会话上下文，因此可以就什么是紧急的与什么可以等待做出明智的决定。
- **对话连续性**：心跳运行共享同一个会话，因此代理可以记住最近的对话并自然地跟进。
- **低开销监控**：一个心跳可以替代许多小的轮询任务。

### 心跳优势

- **批量处理多个检查**：一个代理轮次可以一起审查收件箱、日历和通知。
- **减少 API 调用**：单次心跳比 5 个隔离的 cron 任务更便宜。
- **上下文感知**：代理知道您一直在做什么，并可以相应地确定优先级。
- **智能抑制**：如果不需要关注，代理会回复 `HEARTBEAT_OK` 而不传递任何消息。
- **自然时序**：根据队列负载略有漂移，这对于大多数监控来说是可以的。

### 心跳示例：HEARTBEAT.md 检查清单

```md
# 心跳检查清单

- 检查电子邮件中的紧急消息
- 审查接下来 2 小时内的事件
- 如果后台任务完成，总结结果
- 如果空闲 8 小时以上，发送简短的检查问候
```

代理在每次心跳时读取此内容并在一轮中处理所有项目。

### 配置心跳

```json5
{
  agents: {
    defaults: {
      heartbeat: {
        every: "30m",        // 间隔
        target: "last",      // 在何处传递告警
        activeHours: { start: "08:00", end: "22:00" }  // 可选
      }
    }
  }
}
```

请参阅 [Heartbeat](/gateway/heartbeat) 了解完整配置。

## Cron：精确调度

Cron 任务在**精确时间**运行，并可以在不影响主上下文的情况下在隔离会话中运行。

### 何时使用 cron

- **需要精确时间**："每周一上午 9 点发送此消息"（而不是"9 点左右"）。
- **独立任务**：不需要对话上下文的任务。
- **不同的模型/思考**：需要更强大模型的繁重分析。
- **一次性提醒**：使用 `--at` "在 20 分钟后提醒我"。
- **嘈杂/频繁的任务**：会混乱主会话历史的任务。
- **外部触发器**：无论代理是否处于活动状态都应独立运行的任务。

### Cron 优势

- **精确时间**：5 字段 cron 表达式，支持时区。
- **会话隔离**：在 `cron:<jobId>` 中运行，不会污染主历史。
- **模型覆盖**：每个任务使用更便宜或更强大的模型。
- **传递控制**：可以直接传递到频道；默认情况下仍将摘要发布到主会话（可配置）。
- **无需代理上下文**：即使主会话空闲或已压缩也能运行。
- **一次性支持**：用于精确未来时间戳的 `--at`。

### Cron 示例：每日早晨简报

```bash
moltbot cron add \
  --name "早晨简报" \
  --cron "0 7 * * *" \
  --tz "America/New_York" \
  --session isolated \
  --message "生成今天的简报：天气、日历、重要邮件、新闻摘要。" \
  --model opus \
  --deliver \
  --channel whatsapp \
  --to "+15551234567"
```

这在纽约时间上午 7:00 准确运行，使用 Opus 保证质量，并直接传递到 WhatsApp。

### Cron 示例：一次性提醒

```bash
moltbot cron add \
  --name "会议提醒" \
  --at "20m" \
  --session main \
  --system-event "提醒：站立会议在 10 分钟后开始。" \
  --wake now \
  --delete-after-run
```

请参阅 [Cron 任务](/automation/cron-jobs) 了解完整的 CLI 参考。

## 决策流程图

```
任务是否需要在精确时间运行？
  是 -> 使用 cron
  否  -> 继续...

任务是否需要与主会话隔离？
  是 -> 使用 cron (isolated)
  否  -> 继续...

此任务可以与其他定期检查一起批量处理吗？
  是 -> 使用 heartbeat（添加到 HEARTBEAT.md）
  否  -> 使用 cron

这是一次性提醒吗？
  是 -> 使用带 --at 的 cron
  否  -> 继续...

它需要不同的模型或思考级别吗？
  是 -> 使用带 --model/--thinking 的 cron (isolated)
  否  -> 使用 heartbeat
```

## 结合两者

最高效的设置会使用**两者**：

1. **Heartbeat** 处理常规监控（收件箱、日历、通知），每 30 分钟进行一次批量处理。
2. **Cron** 处理精确调度（每日报告、每周审查）和一次性提醒。

### 示例：高效的自动化设置

**HEARTBEAT.md**（每 30 分钟检查一次）：
```md
# 心跳检查清单
- 扫描收件箱中的紧急邮件
- 检查接下来 2 小时内的日历事件
- 审查任何待处理任务
- 如果安静 8 小时以上，进行简短检查
```

**Cron 任务**（精确时间）：
```bash
# 每天早上 7 点的早晨简报
moltbot cron add --name "早晨简报" --cron "0 7 * * *" --session isolated --message "..." --deliver

# 每周一上午 9 点的每周项目审查
moltbot cron add --name "每周审查" --cron "0 9 * * 1" --session isolated --message "..." --model opus

# 一次性提醒
moltbot cron add --name "回电" --at "2h" --session main --system-event "回电给客户" --wake now
```


## Lobster：具有审批的确定性工作流

Lobster 是**多步骤工具管道**的工作流运行时，需要确定性执行和显式审批。
当任务不仅仅是单个代理轮次，并且您想要具有人工检查点的可恢复工作流时，请使用它。

### Lobster 适合的场景

- **多步骤自动化**：您需要固定的工具调用管道，而不是一次性提示。
- **审批门控**：副作用应该暂停，直到您批准，然后恢复。
- **可恢复运行**：继续暂停的工作流，而无需重新运行早期步骤。

### 它如何与心跳和 cron 配合

- **Heartbeat/cron** 决定运行*何时*发生。
- **Lobster** 定义运行开始后发生的*步骤*。

对于定期工作流，使用 cron 或 heartbeat 来触发调用 Lobster 的代理轮次。
对于临时工作流，直接调用 Lobster。

### 运维说明（来自代码）

- Lobster 作为**本地子进程**（`lobster` CLI）在工具模式下运行，并返回 **JSON 包络**。
- 如果工具返回 `needs_approval`，您可以使用 `resumeToken` 和 `approve` 标志恢复。
- 该工具是一个**可选插件**；通过 `tools.alsoAllow: ["lobster"]` 附加启用（推荐）。
- 如果您传递 `lobsterPath`，它必须是**绝对路径**。

请参阅 [Lobster](/tools/lobster) 了解完整用法和示例。

## 主会话与隔离会话

心跳和 cron 都可以与主会话交互，但方式不同：

| | Heartbeat | Cron (main) | Cron (isolated) |
|---|---|---|---|
| 会话 | 主 | 主（通过系统事件） | `cron:<jobId>` |
| 历史 | 共享 | 共享 | 每次运行都是新的 |
| 上下文 | 完整 | 完整 | 无（从头开始） |
| 模型 | 主会话模型 | 主会话模型 | 可以覆盖 |
| 输出 | 如果不是 `HEARTBEAT_OK` 则传递 | 心跳提示 + 事件 | 摘要发布到主会话 |

### 何时使用主会话 cron

当您想要以下内容时，将 `--session main` 与 `--system-event` 一起使用：
- 提醒/事件出现在主会话上下文中
- 代理在下一次心跳期间使用完整上下文处理它
- 没有单独的隔离运行

```bash
moltbot cron add \
  --name "检查项目" \
  --every "4h" \
  --session main \
  --system-event "是时候进行项目健康检查了" \
  --wake now
```

### 何时使用隔离 cron

当您想要以下内容时，使用 `--session isolated`：
- 没有先前上下文的干净状态
- 不同的模型或思考设置
- 输出直接传递到频道（默认情况下摘要仍发布到主会话）
- 不会混乱主会话的历史

```bash
moltbot cron add \
  --name "深度分析" \
  --cron "0 6 * * 0" \
  --session isolated \
  --message "每周代码库分析..." \
  --model opus \
  --thinking high \
  --deliver
```

## 成本考虑

| 机制 | 成本特征 |
|------|----------|
| Heartbeat | 每 N 分钟一个轮次；随 HEARTBEAT.md 大小缩放 |
| Cron (main) | 将事件添加到下一次心跳（没有隔离轮次） |
| Cron (isolated) | 每个任务一个完整的代理轮次；可以使用更便宜的模型 |

**提示**：
- 保持 `HEARTBEAT.md` 小巧以最小化 token 开销。
- 将类似的检查批量处理到心跳中，而不是多个 cron 任务。
- 如果您只想要内部处理，请在心跳上使用 `target: "none"`。
- 为常规任务使用带有更便宜模型的隔离 cron。
